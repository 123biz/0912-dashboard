## 1. 개요

서울 시내 10개 대리점의 가전 품목 매출을 **한 화면에서 파악**할 수 있는 읽기 전용 웹 대시보드.

가상(synthetic) 데이터 기반의 데모 프로젝트이며, 실제 사업 데이터 연동은 범위 밖이다. 다만 스키마와 집계 구조는 실데이터로 교체해도 그대로 동작하도록 설계한다.

### 해결하려는 문제

대리점별·품목별 매출이 DB 테이블로만 존재하면 다음 질문에 답하는 데 매번 SQL을 써야 한다.

- 이번 달 어느 대리점이 가장 잘 팔았나?
- 어떤 품목이 매출을 끌고 있고, 어떤 품목이 죽어 있나?
- 계절을 타는 품목은 무엇이고, 지금이 성수기인가?
- 지난달 대비 성장했나, 꺾였나?

## 2. 목표 / 비목표

### 목표 (In scope)

- **G1.** 기간·대리점·카테고리 필터를 적용한 매출 현황을 단일 화면에서 제공
- **G2.** 대리점 간 실적 비교 및 순위 제시
- **G3.** 품목/카테고리별 매출 구성과 계절 패턴 가시화
- **G4.** 초기 로딩 2초 이내, 필터 조작 시 500ms 이내 반응
- **G5.** Vercel 배포 후 URL 공유만으로 접근 가능 (로그인 없음)

### 비목표 (Out of scope)

- 데이터 입력·수정·삭제 (읽기 전용)
- 사용자 인증 / 권한 분리
- 매출 예측, 이상 탐지 등 ML 기능
- 엑셀/PDF 내보내기 *(v2 후보)*
- 모바일 전용 앱

## 4. 데이터 모델 (확정)

3개 테이블. Star schema — 차원 2 + 팩트 1.

```
dealerships (10행) ──┐
                     ├──< sales (약 9,000행)
products    (10행) ──┘
```

### 4.1 dealerships — 대리점 마스터

| 컬럼 | 타입 | 비고 |
|---|---|---|
| id | bigint PK | |
| name | text | '강남대리점' |
| district | text | 서울 자치구 |
| address | text | |
| manager | text | 점장명 |
| phone | text | |
| opened_on | date | 개점일 |

### 4.2 products — 품목 마스터

| 컬럼 | 타입 | 비고 |
|---|---|---|
| id | bigint PK | |
| sku | text UNIQUE | 'RF-2001' |
| name | text | '양문형 냉장고 830L' |
| category | text | 냉장고 / 세탁기 / TV / 에어컨 / 생활가전 |
| list_price | numeric | 기준가 |
| unit_cost | numeric | 원가 — 마진 분석용 |

### 4.3 sales — 매출 팩트

| 컬럼 | 타입 | 비고 |
|---|---|---|
| id | bigint PK | |
| dealership_id | bigint FK | |
| product_id | bigint FK | |
| sale_date | date | **일별 입도** |
| qty | int | |
| unit_price | numeric | 실거래가 스냅샷 (할인 반영) |
| amount | numeric | `qty * unit_price` 생성 컬럼 |

- UNIQUE(dealership_id, product_id, sale_date)
- 데이터 기간: **2026-01-01 ~ 2026-09-12 (255일)**
- 반영된 현실성: 계절성, 요일 효과, 대리점 규모 편차, 할인 이벤트, 완만한 성장 추세

### 4.4 RLS 정책

세 테이블 모두 RLS 활성화 + `anon`/`authenticated` SELECT 허용. 쓰기 정책 없음.

## 5. 데이터 접근 계층 (중요)

> **원칙: 집계는 Postgres에서 수행한다. 브라우저로 원시 행을 끌어오지 않는다.**

PostgREST는 GROUP BY를 지원하지 않으므로, 필터 파라미터를 받는 **RPC 함수**로 집계 엔드포인트를 구성한다. 프론트는 수십 행만 수신한다.

공통 파라미터: `p_from date`, `p_to date`, `p_dealer_ids bigint[]`, `p_categories text[]`
(배열 파라미터가 NULL이면 전체를 의미)

| 함수 | 반환 | 소비 화면 |
|---|---|---|
| `get_kpi_summary` | 총매출, 총수량, 평균단가, 거래일수, 직전 동일기간 대비 증감률 | KPI 카드 |
| `get_monthly_trend` | month, revenue, qty | 추이 차트 |
| `get_sales_by_dealer` | dealership, revenue, qty, share | 순위 차트 + 테이블 |
| `get_sales_by_category` | category, revenue, share | 도넛 |
| `get_sales_by_product` | product, category, revenue, qty | 품목 Top 차트 |
| `get_sales_by_dow` | dow, avg_revenue | 요일 차트 |
| `get_dealer_category_matrix` | dealership, category, revenue | 히트맵 |

**성능 요구:** 각 함수는 전체 기간 기준 200ms 이내 응답. `sales(sale_date)`, `sales(dealership_id, sale_date)`, `sales(product_id, sale_date)` 인덱스로 커버.

## 6. 화면 설계

단일 페이지(SPA), 세로 스크롤 구성.

```
┌──────────────────────────────────────────────────┐
│  헤더 — 타이틀 / 데이터 기준일                     │
├──────────────────────────────────────────────────┤
│  필터 바  [기간] [대리점 ▾] [카테고리 ▾] [초기화]  │  ← sticky
├──────────────────────────────────────────────────┤
│  KPI  ┌─총매출─┐┌─판매수량─┐┌─평균단가─┐┌─1위점─┐ │
│       │ +12.4% ││  -3.1%  ││  +2.0%  ││ 강남  │ │
├──────────────────────────────────────────────────┤
│  월별 매출 추이 (Area, 전폭)                       │
├────────────────────────┬─────────────────────────┤
│  대리점별 매출 순위     │  카테고리 구성 (Donut)   │
│  (가로 Bar)            │                         │
├────────────────────────┼─────────────────────────┤
│  품목 Top 10 (가로 Bar)│  요일별 평균 매출 (Bar)  │
├──────────────────────────────────────────────────┤
│  대리점 × 카테고리 히트맵                          │
├──────────────────────────────────────────────────┤
│  상세 테이블 (대리점별 매출/수량/비중, 정렬 가능)   │
└──────────────────────────────────────────────────┘
```

### 6.1 컴포넌트 요구사항

| 컴포넌트 | 요구사항 |
|---|---|
| **필터 바** | 기간은 프리셋(최근 30일/3개월/전체) + 직접 선택. 대리점·카테고리는 다중 선택. 상태를 URL 쿼리스트링에 반영해 **링크 공유 시 동일 화면 재현**. |
| **KPI 카드** | 값 + 직전 동일 길이 기간 대비 증감률. 증가는 상승 아이콘/녹색, 감소는 하강/적색. |
| **추이 차트** | 월별 매출 Area. 툴팁에 매출·수량 동시 표기. |
| **순위 차트** | 가로 막대, 매출 내림차순. 막대 클릭 시 해당 대리점으로 필터 적용. |
| **도넛** | 카테고리 5종. 범례에 금액·비중 병기. |
| **히트맵** | 행=대리점, 열=카테고리. 색 농도=매출. 빈 셀은 미취급으로 표시. |
| **상세 테이블** | 컬럼 정렬 가능. 금액은 천 단위 구분·원화 표기. |

### 6.2 상태별 UI

- **로딩** — 각 차트 영역에 스켈레톤
- **빈 데이터** — "선택한 조건에 해당하는 매출이 없습니다" + 필터 초기화 버튼
- **에러** — 에러 메시지 + 재시도 버튼 (차트 단위로 격리, 전체 화면 붕괴 금지)

## 7. 기술 스택

| 영역 | 선택 | 선정 사유 |
|---|---|---|
| 빌드 | **Vite** | 읽기 전용 정적 SPA에 SSR 불필요. HMR 빠름 |
| UI | **React 19 + TypeScript** | |
| 차트 | **Recharts** | React 컴포넌트 API, 이 규모에 충분 |
| 데이터 | **@supabase/supabase-js** | RPC 호출 |
| 서버 상태 | **@tanstack/react-query** | 캐싱·중복요청 제거·로딩상태 일원화 |
| 스타일 | **Tailwind CSS** | |
| 배포 | **Vercel** | 정적 빌드 + Git 연동 자동 배포 |

### 선택하지 않은 것

- **Next.js** — SSR/서버라우트/SEO/인증 중 필요한 것이 없음. 오버엔지니어링
- **ECharts** — 지도 시각화를 하지 않으므로 이점 없음. 설정 비용만 증가
- **Redux 등 전역 상태** — 서버 상태는 React Query가, 필터 상태는 URL이 관리

## 9. 배포

### 환경변수

```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ...
```

- 로컬은 `.env.local`, 운영은 Vercel 프로젝트 환경변수에 등록
- `.env*`는 `.gitignore`에 포함
- `VITE_` 접두사가 붙은 값은 **번들에 그대로 노출**됨 — anon key 외에는 넣지 않는다

### 배포 절차

1. GitHub 리포지토리 연결
2. Vercel 프로젝트 생성 → Framework Preset: Vite
3. Build Command `npm run build`, Output Directory `dist`
4. 환경변수 등록 후 배포
5. `main` 브랜치 푸시 시 자동 재배포
